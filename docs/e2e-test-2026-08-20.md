## Verdict

The 2026-08-19 regression pass genuinely fixed what it claimed to fix — I re-verified eight of its claims live and all eight held up. But this pass also surfaced two new, previously undocumented bugs (one visual, one a duplicate-content issue on the Ask page), reconfirmed that the personalization "why this?" explanation is still misleading in the exact way the original audit described, and confirmed the Ask relevance engine still returns confident results for a nonsense query. None of these are regressions in the sense of "broke something that worked" — they're either newly introduced by the hardening pass's own changes, or gaps the regression pass didn't attempt to close.

## New issues found in this pass

### 1. Ask results duplicate an entity between the Journey and "Best matches"

For any query that triggers both the relevance search *and* the Connected Journey builder — which includes a large share of realistic queries (anything matching AI/tech, founders, entrepreneurship, or discovery-style phrasing) — the same entity can appear twice on one results page: once as a Journey step, once again in "Best matches" directly below it.

Reproduced with the query **"Big Red AI"**: the Journey path shows Big Red AI (step 1) and Generative AI at Cornell (step 2); the "Best matches" grid immediately below shows Big Red AI and Generative AI at Cornell again as the top two cards. Root cause: `askView()` renders `journeyView(journey)` and `groupedResults(results)` independently — the journey is built from `buildJourney(query)` and the grouped results from `searchEntities(query)`, and nothing deduplicates entities that both paths happen to select. This looks like a side effect of the 2026-08-19 change that reordered "Best matches" to appear before category groupings — that fix solved the original problem (best matches buried under groupings) but didn't account for the journey section sitting above both.

*Screenshot: entities repeated between the Journey path and Best matches for "Big Red AI."*

**Recommended fix:** when a journey is shown, exclude its step entities from `groupedResults`, or merge the two into one deduplicated results view.

### 2. Ask still answers a nonsense query with confident, unhedged "Best matches"

Query: **"Find me a Cornell fencing tournament on Mars."** The app responds "I found 3 resources in events and connected areas" and shows three "Best matches" cards (Cornell ClubFest, Cornell Events, Cornell Innovation & Entrepreneurship Workshops) — Cornell's entire Events category — with no hedge, no acknowledgment that the query doesn't make sense, and no distinction from a real match.

This is the same failure mode the 2026-08-19 audit flagged under "Ask can sound confident when it should say 'no match'" (finding #3), and it's still open despite that same pass improving the *temporal* honesty case ("what's happening this week?" now degrades gracefully, see above). Root cause, confirmed by reading `interpretQuery()` / `searchEntities()`: the word "tournament" alone matches the events-category regex (`/(event|happening|this week|tonight|workshop|tournament)/`), which sets `intent.category = "events"`. The results filter is `score >= 5 && (directMatches > 0 || (intent.category && primaryDomainFor(entity) === intent.category))` — the `OR` means a bare category-keyword match is enough to pass the entity through with zero actual relevance to the rest of the query. Any query containing one of those trigger words returns the *entire* matching category, regardless of how irrelevant the rest of the sentence is.

**Recommended fix:** require at least one direct term match in addition to a category-keyword match before treating a query as "confident," per the original audit's recommendation; reserve the category-only path for an explicit "browse this category instead" fallback with different, hedged copy.

### 3. Personalization's "why this?" reason still cites the wrong signal

With AI/Technology and Entrepreneurship selected as interests, none of the five Discover-page cards attributed their selection to "Matches your interest in…" — every card that was also linked to a recently-viewed entity showed "Related to [that entity]" instead, even in at least one case where the entity was also a genuine interest match. Root cause: `discoveryReason()` checks `relatedToAnchor` before `matchedProfileInterest`, so browsing-history relevance always wins the display slot over declared-interest relevance when both apply — even though `discoverEntities()` itself may have picked the entity via the interest-matching loop. This is a live reconfirmation of audit finding #7 ("Explain the actual matching factor, not the first selected interest") — not something the regression pass attempted to address, and still not addressed.

### 4. New visual bug: Discover-page card captions collide with the row below

On the Discover page, the "reason" caption under a discovery card (e.g., "Related to Big Red AI") can be partially hidden behind the top edge of the next row's card. Reproduced and confirmed with a pixel-level crop (see screenshot). Root cause, from `styles.css`: `.entity-card-shell { height: 100%; }` stretches each card to fill its grid row's full track height; when cards in the same row have different content lengths, the shorter card's trailing `.discovery-reason` caption gets pushed down far enough to spill past the row boundary set by the grid's own track sizing, landing under the next row's card. It's data-dependent — it did not reproduce on the home page's discovery section in this same session (that row's cards happened to be more even in height) — which is why it likely wasn't caught before; it will recur any time a discovery/related row has one notably shorter card.

**Recommended fix:** don't stretch `.entity-card-shell` to 100% height when a sibling caption follows it in the same grid cell, or move the reason caption inside the card shell's own box so grid track sizing accounts for it.

### 5. Minor: custom URL validation message is shadowed by the browser's native one

Typing an invalid value into the university URL field and submitting shows Chrome's generic native tooltip ("Please enter a URL.") instead of the app's own message ("Enter a valid university website URL, including https://"). The input's native `type`/pattern constraint fails before the form's submit handler (which calls `setCustomValidity(...)`) ever runs, so the custom copy is unreachable in this path. Submission is still correctly blocked either way — this is a copy/polish gap, not a functional break — but it will also mean the message users see differs by browser (Firefox and Safari phrase native validation messages differently).

## Confirmed still open (unchanged since 2026-08-19, reverified against today's live data)

These were already known and the regression pass didn't claim to fix them — re-verified they're still accurately described:

- **Events have no real dates.** 0 of 3 discoverable Events entities carry a `date.startAt` value. The temporal-honesty fix (finding above) is a good stopgap, but "what's happening" still isn't actually answerable from the dataset.
- **People & Networks has zero individual people.** All 4 members are networks/platforms (CUeLINKS, Cornell Entrepreneur Network, Big Red AI, Cornell StartupTree). The rename makes the category internally honest, but a literal "find people" intent still returns systems, not people.
- **Student-built is still thin.** Exactly 2 discoverable resources (Cornell AppDev Apps, JCT MBA Fall 2026 Course Planner).
- **Trust metadata gaps persist:** 5 of 43 relationships remain medium-confidence with no evidence URLs (validator surfaces these as warnings, correctly); 25 of 42 entities have no `audience` field; 0 entities carry eligibility or deadline data.
- **No hosted deployment.** Still local-only; not testable as a public URL.

## Testing limitations this pass

- **No live `npm run build` or `npm run dev` run.** This session's device shell didn't come up, and this sandbox's package registry is blocked, so I substituted a static-serve harness that runs the actual source files unmodified except for the CSS-import mechanism. I'd still recommend running `npm run build` locally before the next demo, just to have a current, first-party confirmation.
- **No live external-link health check.** This sandbox has no outbound network access to arbitrary domains (confirmed: Google Fonts and the npm registry both failed at the connection level). The 2026-08-19 regression pass reported 37/37 primary action URLs returning 2xx; that hasn't been re-verified today. There's also no automated link-checker script in `scripts/` yet — right now this check has been done by hand each time. Worth adding a small script (e.g. `scripts/check-links.mjs`) that walks every entity's primary/provenance URL and reports non-2xx responses, so this stops being a manual step before each review.

## Suggested priority order

1. Fix the Ask duplicate-entity issue (#1) — quick, mechanical, affects a large share of real queries.
2. Tighten the category-keyword-only match path in `searchEntities()` (#2) — this is the last piece of the original "confident wrong answer" problem from 2026-08-19.
3. Fix the Discover-page card/caption collision (#4) — a real visual bug a judge or student could hit at any time depending on which cards happen to be selected.
4. Reorder `discoveryReason()` to prefer the actual selection reason over "Related to" when an interest match exists (#3).
5. Polish the URL-validation message path (#5) — low effort, low risk.
6. Add an automated link-health script so future audits don't depend on a one-off manual pass.

## Follow-up resolution — 2026-08-20

The first five issues above were resolved in the subsequent local-only hardening patch:

- Ask now omits any entities already shown in a Connected Journey from the result groups below it.
- Ask rejects a query containing an unsupported specific term instead of using one broad category word to return confident results. The temporal calendar handoff follows the same guard.
- Discovery explanations now prioritize a declared interest match over browsing-history relatedness.
- Discovery cards no longer stretch their card shell when a reason caption follows, so the caption remains within its own grid item.
- Profile and onboarding forms use application-controlled validation, allowing the consistent URL message to be shown before the browser's native tooltip.

Verification after the patch: `npm run validate:data`, `npm run build`, `node --check src/main.js`, and `git diff --check` completed successfully. A second in-app-browser pass could not run because the browser's local-URL policy rejected the restarted local server; no workaround was used. The known dataset coverage gaps listed above remain open and are not represented as fixed.
